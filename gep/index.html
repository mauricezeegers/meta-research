Part 2: Reference SOP

We use a consistent way of working for every project. The aim is to make collaboration easier, keep project materials organised, improve reproducibility, and facilitate open sharing of research outputs. Every project uses three environments, each with one clear purpose: Cloud for internal work and collaboration, GitHub for code, Open Archive for what is shared publicly. The cloud provider and archive may differ between projects (OneDrive, SharePoint, Google Drive … / OSF or similar). The structure below stays the same.

1. Cloud: internal working environment

The project's Cloud environment (UM OneDrive/SharePoint, Google Drive, or another service with sufficient protection and version control) is where the team collaborates on materials not intended for public access: project administration, ethics & regulatory documents, meeting notes, working versions of protocols and Statistical Analysis Plans, manuscript drafts, and the project's master dataset.

The master dataset lives in the Cloud as the single official source of the data. Researchers work from a local copy when analysing it. The master dataset is, as a rule, not stored on GitHub. Exceptions are possible only in a private repository and only when agreed with Maurice Zeegers. Once a dataset is final and no longer changes, it can be treated as read-only.

Suggested folder structure (share the top level with the supervisory team):

Project 1 (usually one dataset)
AdminProtocol (incl. previous versions), ethical documents, etc.
DataMaster dataset only (raw, preferably CSV). All conversions happen via code, not by hand.
Paper 1, Paper 2 …Manuscript drafts (keep previous versions). Code lives on GitHub (see §2), not here.
Project 2 …Same structure

2. GitHub: code & reproducible output

GitHub is the version-controlled environment for research code and reproducible output. Each project gets its own private repository with the same basic structure:

code/Data import, cleaning, variable construction, statistical analysis, functions & supporting code. One file per paper, with extensive comments (R Markdown). Git tracks every change automatically: what changed, when, by whom, and which version produced which result.
output/Reproducible outputs generated by the code: tables, figures, statistical output, reports.

Not stored on GitHub: administrative documents, manuscript drafts, or other internal working material. Those stay in the Cloud (§1). Research data are, as a rule, not stored on GitHub either (see §1). Access is granted per project to authorised researchers and collaborators.

3. Open Archive: open sharing

The Open Archive (Open Science Framework, or another open-science platform with sufficient protection and version control) is for research materials shared with the wider research community or the public. Make a separate Open Archive project per project/dataset, and share it with the supervisory team:

  • Metadata: Title, Description, Contributors (co-authors), Project DOI
  • Registrations: final protocol (posted before data collection), amendments (after). The final protocol can also be published as a preprint on MetaArXiv or medRxiv.
  • Contributors: add as many co-authors as possible to the Open Archive project

The Cloud is where documents are developed and maintained. The Open Archive is where their final, shareable versions are published.

One file, one home

Each file or document has exactly one primary home, to avoid competing copies:

FileHome
ProtocolDeveloped & revised in the Cloud, final/public version on the Open Archive
Analysis codeDeveloped & version-controlled on GitHub. No separate working copies in the Cloud.
Master datasetCloud. Local copies for analysis. On GitHub only by exception (see §1).
Internal administrationCloud only, unless there's a specific reason to share it elsewhere

Access, in general: Cloud for the project team. GitHub for authorised project researchers & collaborators. Open Archive for wider/public access, but only to what is meant to be shared. Exact access may differ per project depending on the ethical, legal and institutional requirements that apply.

4. Publications

4.1 Last checks just before submission

The first or corresponding author checks that the data and code lead to the reported results, checks for unintended plagiarism (via the UM similarity check, using your UM account), and checks AI use (via Pangram).

4.2 Disclosures (if relevant)

AIDisclosure: tool name, version, purpose (see CANGARU). E.g. “No AI was used in language editing, data collection, analysis or the writing of this manuscript. Zotero was used for automatic referencing and to identify potentially retracted papers. All authors declare responsibility for the content generated by AI.”
Competing interestsAsk every author for their CoI. All authors express their own opinions, not necessarily those of their funders or employers.
FundingStandard funding statement related to the dataset, plus any other funding.
Ethical approvalE.g. “This study was designed according to the Declaration of Helsinki and received ethical approval from #### Committee, number ####.”
AcknowledgementsStandard acknowledgement statement related to the dataset, plus any others.
Data & materials availabilityE.g. “The protocol and associated resources of this study can be found on the Open Archive (add DOI). Restrictions apply to the availability of these data, which were used under licence for the current study. Data are, however, available from the authors upon reasonable request and with permission of the ### management team.”
CRediTAuthor contributions, see this taxonomy.
Patient & Public InvolvementE.g. “Patients or members of the public were not involved in the design, conduct, reporting, or dissemination plans of this research” or, if they were, describe how (consultation, feedback, what informed which decisions).

4.3 Where to publish

The aim is a peer-reviewed scholarly work, not a particular journal or journal rank. A journal is one route. A preprint or other citable version with a DOI that is peer reviewed afterwards, in the open, is equally acceptable. If you choose a journal and publication charges apply, we only submit to journals with a 100% APC discount deal with UM (see the Open Access Journal Browser), or to a closed-access journal with no submission fee.

4.4 Open access

In principle we don't pay a journal directly for open access. Instead, every UM staff member and (external) PhD student signs up for Maastricht University's Open Access Green Route (Taverne). Under Dutch copyright law this makes all papers open access after 6 months, even behind a paywall. Remember to opt out of “early view” in Wiley journals.
